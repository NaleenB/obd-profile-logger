## Project

A read-only OBD-II logger for iOS and macOS. It reads standard OBD on any
compatible car, and manufacturer data through JSON vehicle profiles — currently a
2016 Mitsubishi Outlander 2.2 DiD (4N14), verified on the car.

Purpose is preventive: record continuously, compare against real limits, and
surface drift before something fails. Not a performance logger, not a tuning tool.

## Layout

```
profiles/   per-vehicle JSON — the extension point; a car is data, not code
Core/       OBDCore: models, health rules, decoders, recorder (file I/O only)
Link/       OBDLink: BLE transport, ELM327 client
App/        SwiftUI app for iOS and macOS; project generated from project.yml
Probe/      macOS CLI: capability discovery, identifier sweeps, sensor checks
tools/      profile generator, icon renderer, iOS deploy script
docs/       protocol, session format, architecture, checklists
Research/   how the manufacturer data was obtained
```

`Core` and `Link` are separate Swift packages so another front end can adopt them
independently. `App/OBDLogger.xcodeproj` is generated by XcodeGen from
`project.yml` and is gitignored; never hand-edit it.

## Invariants

These are not preferences. Breaking one produces confident wrong answers.

**Read-only.** No service `2E`, `2F` or `31`. No writes, no actuator tests, no
forced regenerations. A wrong write can damage a vehicle and this tool is used by
people who are not mechanics.

**Frames stay separate.** Two ECUs answer one broadcast request on this car
(`7E8` engine, `7E9` transmission). Concatenating their replies fabricates fault
codes and corrupts multi-byte values. Take one frame per module.

**Absence of a sample means the read failed.** Never write a zero or repeat a
previous value. But distinguish *not attempted* from *failed*: a parameter the
sweep never reached is not a failed read. `sweep_completed` events exist for this.

**Provenance is explicit.** Every finding carries `.serviceManual(item:)` or
`.heuristic(...)`. An inference must never be presented with a specification's
authority.

**Freshness.** A health check may only use a reading within its age budget and
under the stated operating condition. `ReadingSet.fresh` and `LiveReadings.isStale`
exist for this.

**NDJSON is canonical.** One JSON object per line, append-only. CSV is only ever
generated at export. A crash costs one line; a decode bug can be fixed by
reprocessing history rather than re-driving the car.

## Domain facts already established

Do not re-derive these. Full detail in `../OUTLANDER.md` and `docs/protocol-notes.md`.

- Adapter: Viecar BLE clone, `ELM327 v1.5`, `AT@1` = `ICSolution`, Microchip
  `IS1678S152`. BLE serial port is `FFF0` / `FFF1` notify / `FFF2` write.
- Bus: ISO 15765-4 CAN 11/500. Pin `ATSP6`.
- Standard OBD exposes 26 PIDs and nothing above `0x4E`. **No DPF, EGT or oil
  temperature through mode `01` on this car.**
- Manufacturer data is service **`0x21`**, one-byte local identifier. Service
  `0x22` is not implemented (NRC `0x11`).
- Byte offsets in the profile are **absolute within the response frame**, counting
  the `0x61` service byte and the LID.
- **`ATH1` latches this clone's CAN receive filter** to the last responder and
  `ATH0` does not clear it. Restore with `ATAR` then `ATSH7DF`. Header scans
  therefore run last, or they hide every other module for the session.
- **PM filter monitoring is not supported** (readiness byte C bit 6 clear), so
  P2002/P2463 can never appear here. Comprehensive component monitoring is
  supported but incomplete. Code absence says nothing about the DPF.
- Charging is **current-sensor controlled**: it reaches ~14 V then floats to
  ~12.6 V when the battery is full. Do not flag that as an alternator fault.

## Profile selection

**There is no profile picker, and no assumption path.** The app starts on generic
OBD and applies a specific profile only when the car proves it. Implemented in
`ProfileResolver`, `ProfileMatcher` and `LiveModel.attemptIdentification`:

1. Calibration ID (mode `09` PID `04`) — sharpest, because byte layouts follow the
   ECU software version.
2. VIN prefix, longest match wins.
3. **Live-data agreement** — the profile declares a required discriminator in its
   `identity` block (engine speed), which must agree with the ECU's own rpm for
   three consecutive probes. Coolant and plausibility ranges corroborate but never
   decide; a required discriminator below its `minimumStandard` proves nothing
   (engine off agrees on zero).

Unresolved means **standard OBD only**: no manufacturer panel, no manufacturer
samples. Identification is retried on a schedule (0, 15, 30, 60, 120, 300 s) so a
cold ECU resolves when it wakes, then stops. A session can therefore start generic
and resolve while recording; the boundary is a `profile_changed` event and the
manifest carries the final profile.

**Answering `0x21` is never treated as proof that a profile's offsets apply** — the
same database holds five diesel variants with the DPF block on different
identifiers. A plausible-looking wrong number is the failure mode this whole design
guards against. If calibration matched but live data contradicts the layout, the
profile stays and a `profile_disagreement` event records the evidence.

Developer override, never reachable from the interface:

```bash
defaults write com.naleen.obdlogger ProfileOverride mitsubishi-outlander-2016-4n14
```

## Data contracts

A session directory holds `manifest.json`, `samples.ndjson`, `events.ndjson` and
`profile.json` (a copy of the decoding rules). Sessions live in Application
Support; the Mac and the phone have separate stores with no sync.

`SampleRecord` carries `pid` **or** `service`+`lid`, plus `value`, `unit` and the
raw frame. `schemaVersion` is 4. See `docs/session-format.md` before changing a
field — bump the version when a field's meaning changes, not when one is added.

## Build, test, deploy

```bash
cd Core && swift test            # domain, recorder and profile tests
cd Link && swift test            # ELM327 response parser tests
cd Probe && swift test           # Probe safety tests, no car needed
cd Probe && ./run.sh --self-test # parser checks; exits non-zero on failure
cd App && ./run.sh               # build and launch the macOS app
cd App && xcodebuild test -project OBDLogger.xcodeproj -scheme OBDLogger-macOS \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO  # coordinator state tests
./tools/deploy-ios.sh            # bump version, build, install to iPhone
cd App && xcodegen generate      # after editing project.yml
```

CI (`.github/workflows/ci.yml`) runs Core, Link and Probe tests, the Probe
self-test, the macOS app coordinator tests and both app builds for every push and
pull request. It needs no adapter, so a regression in parsing, decoding, profile
validation, session-boundary state or packaging is caught before hardware.
Connection-generation ownership still has to be exercised on hardware.

`deploy-ios.sh` increments the patch version before building, so the version on
screen always matches the installed build. The build number (`CFBundleVersion`) is
manual and currently inert.

macOS builds have no expiry. iOS uses free provisioning: a 7-day profile, and
re-running from Xcode is an **upgrade** that preserves the app container.
Deleting the app destroys every recorded session.

Pulling sessions off the phone without the share sheet goes through
`tools/pull-ios-sessions.sh`, which archives them under `sessions/` (gitignored):

```bash
./tools/pull-ios-sessions.sh [<udid>]
```

Every read of the device log is archived there first; a `/tmp` copy is only a
fallback when the device is unreachable. The archive merges rather than
replaces, because NDJSON is append-only: a later pull completes an interrupted
session, and a session deleted from the phone stays in the archive.

## Known traps

Each of these has already caused a wrong conclusion.

- **The median sample interval lies.** Two manufacturer polls per cycle produce a
  bimodal gap distribution; the median reads 182 ms while the average is 814 ms.
  Report throughput as samples divided by elapsed, never as the median interval.
- **A free-rev Δp test tells you nothing.** Exhaust flow in neutral is roughly a
  third of loaded flow, and Δp scales with flow. A healthy filter reads near zero
  there. Only loaded driving characterises the sensor.
- **Both soot figures are ECU models, not tool calculations.** Item 155 is an
  open-loop accumulator that only grows unless a regeneration subtraction fires;
  item 156 is differential-pressure based. They are not two estimates of the same
  quantity and must not be compared with a simple ratio rule.
- **Cranking minimums are sampled, so they can only be too high.** Do not claim a
  threshold was cleared from a 2 Hz capture.
- **Ignition-on voltage is not a resting measurement** (glow plugs plus ECU load).
  The battery check compares it against 11.8 V, not the 12.2 V resting band.
- **Raw `230` is a sentinel, not 950 °C.** It appears on the NTC input this car
  does not have and on the stored-maximum fields, while live temperatures read
  normally and regen peaks sit at 620–720 °C. Those parameters declare
  `unavailableRaw` so they are dropped instead of shown.
- **Regeneration thresholds (450 °C start, 300 °C end) are conventional**, not
  measured on this car.
- **Two session events can mean one trip.** A dropped link now reconnects and
  continues the same session; do not assume a new session means a new drive.
- **A cold start used to spend ~28 s before the first sample**, because the DPF
  read and trip snapshot ran before polling. They now wait for the first
  successful sample. If startup is slow again, check `startup_timing` events
  before guessing: a slow scan and a slow ECU look identical without them. Every
  field there is a stage duration except `totalMs`; the manufacturer probe is
  split by command because two header commands costing seconds means a busy
  adapter, not a slow car. `first_sample` must use the first successful
  observation's timestamp, not `lastUpdate` after enrichment.
- **One battery report per engine cycle, not per connection.** The monitor resets
  after the engine has been stopped for five seconds, so a restart in the same
  connection is measured again.
- **A silent car is not a hung app, and used to look exactly like one.** With the
  ignition off the ECU sleeps while the adapter keeps answering "NO DATA" in
  ~270 ms; the link is healthy and nothing is ever recorded. Two things made this
  look like a freeze: the screen kept showing the last values under "Connected",
  and `DataGapMonitor` was fed only after a successful sample, so the silence it
  measured had just been reset and `data_gap` could never fire. Silence is now
  judged at the top of every loop iteration, announced in the UI after five
  seconds, and after fifteen the loop degrades to `ATRV` plus one rpm probe every
  three seconds until the car answers again. Check `app_lifecycle` and `data_gap`
  before blaming the app.
- **The main screen scrolls because it is wrapped in a `ScrollView`, not because
  it worked before.** "It stopped scrolling" was reported as evidence of a hang;
  the screen had no scroll view at all.
- **An interrupted session used to lie about its own profile.** Manifest fields
  were only written by `finish`, so a killed recording kept the connect-time
  `generic-iso15765-can` / `none` while `profile.json` and every manufacturer
  sample were the Outlander's. `updateManifest` now writes as it changes; if a
  manifest again disagrees with `profile.json`, that write has regressed.
- **The TCM stops answering within a second or two of the engine stopping**, well
  before the ECM does. DTC scans after shutdown are honestly `incomplete` — that
  is the car, not a lost scan. Scan while the engine is running.
- **A data gap ends for a reason, and only one of them is a resumption.** A link
  drop while the car was already silent used to be written as `data_resumed`,
  which made the log claim data that never arrived. `data_resumed` now requires a
  sample; anything else is `data_gap_ended` with a `reason`. Preserve the last
  genuine sample and the gap monitor across reconnection: an outage shorter than
  ten seconds at link loss can still cross the threshold while reconnecting, and
  resetting the monitor erases it from the log.
- **A scan and a connection are one unit.** The scanner is dropped on a link
  loss or a stall, and a cancelled poll task does not commit a step it was
  waiting on. Keeping either would stitch two connections into one DTC result.
- **A reconnect attempt must be replaced, not just invalidated.** If the link
  drops again while the reconnect task is still running, cancelling its epoch
  without releasing its ownership leaves `beginReconnect` blocked forever. Wait
  for the old attempt to relinquish the shared BLE transport, then start a new
  attempt under a new ownership token. A superseded attempt checks ownership after
  every await and stops before its fallback scan or connection; only the attempt
  that still owns the transport closes it. Otherwise a user disconnect can be
  followed by a stale connection behind the "Not connected" screen.
- **Readiness means notifications are subscribed.** The serial port is resolved
  before setup finishes, and a failed or timed-out attempt leaves that port
  behind. A disconnect before subscription completes is a failed attempt, not an
  established-link loss, so readiness is tracked explicitly rather than inferred
  from the port reference.
- **A sweep cycle closes only after its final request has an outcome.** An attempt
  is recorded immediately before sending `21xx`, not while configuring the header.
  Counting before the request reports a LID that was never requested; closing
  before a reply or timeout carries an unanswered request into the next cycle.
- **The start odometer is written when it is read, not at close.** Service `0x21`
  does not answer until the car is identified, so it typically arrives after
  recording starts; without it there is no soot-per-km or regen interval. A
  failed read does not restart the 60 s timer, so a cold ECU is retried promptly.
- **Manufacturer roles belong to the profile, not the app.** Highlights, priority
  blocks, trip snapshots, odometer and DPF meanings are declared under `roles`.
  A profile without them simply exposes less; it is never decoded with another
  vehicle's hard-coded offsets.
- **Probe only sweeps read services.** `21`, `22` and `1A` are allow-listed in
  both argument handling and the sweep itself. Never widen that list to include
  write, actuator or routine-control services.
- **A profile is validated before use.** The loader rejects malformed lengths,
  duplicate LIDs, invalid identity references and `observed` evidence that does
  not match the emitted scaling. A profile that cannot be interpreted safely is
  not allowed to become trusted data.
- **A PID bitmap is authoritative only for its own range.** On 27 Oct 2026 the
  ECU woke part-way through the connect probe: `0100` and `0120` went
  unanswered, `0140` parsed, and the session recorded a confident 7-PID car and
  one dashboard tile instead of 28 PIDs and ten. A range whose bitmap never
  answered is unknown, not unsupported — `PIDDiscovery` filters only what the
  answering bitmaps cover, retries the gap once the ECU is answering, and
  records `unansweredPIDBases` so a partial set cannot be read as the whole car.
  The same session shows the other half of the trap: one connect-time probe is
  not evidence about a service. `2111` timed out while the ECU woke, and the
  manifest claimed `0x21` never answered while 2136 manufacturer samples sat
  below it.
- **A manual connect starts a new vehicle session; an in-session reconnect does
  not.** `connect()` resets to the generic profile and clears the previous car's
  match, diagnostics and odometer state. Reusing a resolved profile was
  decoding a different car with the Outlander's offsets and stamping
  `profileMatch: calibration` without reading a calibration ID. `beginReconnect`
  deliberately preserves the profile because it is still the same car.
- **Standard OBD is addressed to the engine, not read from the first broadcast
  frame.** Both `7E8` and `7E9` answer `7DF`; `payloadHex` takes the first, so a
  TCM reply could become vehicle speed, rpm or the capability bitmap. The
  profile's `engineRequestHeader` (or `7E0` on 11-bit CAN) is selected for mode
  `01`, identity, ambient and discovery. The 11-bit `7E0` must not be sent on
  29-bit CAN or a non-CAN bus; a 29-bit profile has to name its own engine
  header. Do not enable `ATH1` to solve this: it latches this clone's receive
  filter.
- **Battery inputs belong to one polling cycle.** A fresh voltage beside a cached
  RPM hides a crank; a fresh RPM beside a cached voltage records a crank minimum
  from seconds earlier. `BatteryCycle` carries `nil` for a failed read, and the
  monitor is fed once per cycle. A link drop does not reset `batteryLogged`:
  Bluetooth dropping is not the engine stopping.
- **Discovery improvements are persisted immediately.** A cold-start retry can
  turn a failed/partial pass into a complete one mid-session. Writing that only
  at stop leaves an interrupted manifest claiming the car had fewer PIDs than
  its samples used.
- **A peripheral UUID is not a connection identity.** Reconnecting to the same
  adapter reuses the same `CBPeripheral`; the old `didDisconnect` can arrive
  after the replacement is installed and tear it down. `BLETransport` waits for
  the previous teardown callback before reusing the UUID.

## Status — what is proven

Verified on the car: standard recording, manufacturer decode, DPF values, injector
learning, rail pressure, turbo boost, DTC scanning on both ECUs, battery test, ZIP
export, locked-screen background recording on the iPhone.

`ReferencePointDetector` and the general `HealthEvaluator` paths are retained for
baseline learning but are not wired into the shipped dashboard; their tests are
not evidence about app behaviour.

Not yet observed: the 10-minute idle disconnect, the 10-minute reconnect window,
regeneration detection against a real regeneration, quiet mode past its entry
(silence is announced and the loop degrades as designed, but the car has not yet
been watched waking back out of it), and the reconnect fallback on a stale
peripheral — that path was duplicated from the manual connect, not induced on the
phone. Connection generations are unit-tested, but superseded BLE callbacks have
not been forced on hardware.

## Conventions

- Swift: no third-party dependencies. `swift test` must pass.
- Python in `tools/`: standard library only.
- Comment *why*, not *what*. Prefer a short explanation over a restated line.
- Do not commit manufacturer software, decrypted databases, bulk captures or
  session data. `.research/` is gitignored and must stay that way.

## Out of scope

Writing to an ECU, actuator tests, forced regenerations, ABS/SRS/AWD/body modules,
emissions certification claims, and anything requiring a manufacturer subscription.
